# MiniWiki — Структура проекта

## 1. Общая организация

Проект MiniWiki организован по модульному принципу. Структура каталогов разделяет бизнес-логику, обработку HTTP-запросов, работу с базой данных, пользовательский интерфейс и автоматические тесты.

Такое разделение упрощает сопровождение, тестирование и дальнейшее расширение приложения.

## 3. Назначение основных компонентов

### 3.1. Каталог app/

Основной каталог приложения.

- `main.py` — создание и настройка экземпляра FastAPI, подключение маршрутов.
- `config.py` — загрузка и управление настройками приложения.
- `database.py` — подключение к базе данных и управление сессиями.

### 3.2. Каталог models/

Содержит модели данных и описание структуры сущностей приложения.

### 3.3. Каталог routers/

Содержит HTTP-маршруты и обработчики запросов.

Маршруты отвечают за получение запросов, проверку входных данных и передачу управления соответствующим сервисам.

### 3.4. Каталог services/

Содержит бизнес-логику приложения.

Сервисы отвечают за создание, редактирование, поиск и удаление wiki-страниц, а также за другие операции с данными.

### 3.5. Каталог templates/

Содержит HTML-шаблоны Jinja2.

### 3.6. Каталог static/

Содержит статические ресурсы приложения, включая CSS, изображения и клиентские файлы.

### 3.7. Каталог tests/

Содержит автоматические тесты.

Тесты разделяются по функциональным областям приложения.

### 3.8. Каталог docs/

Содержит проектную документацию, архитектурные решения и инструкции для разработчиков.

## 4. Файлы конфигурации

- `pyproject.toml` — настройки Python-проекта, Ruff и инструментов разработки.
- `requirements.txt` — основные зависимости приложения.
- `pytest.ini` — настройки Pytest.
- `.env.example` — пример переменных окружения без секретных значений.
- `.gitignore` — список файлов и каталогов, которые не должны попадать в Git.
- `Dockerfile` — инструкция сборки контейнера.
- `docker-compose.yml` — конфигурация запуска приложения и связанных сервисов.
- `README.md` — основная информация о проекте и инструкции по запуску.

## 5. Принципы организации кода

1. Каждый модуль должен иметь одну основную ответственность.
2. Маршруты не должны содержать сложную бизнес-логику.
3. Бизнес-логика должна располагаться в сервисах.
4. Модели данных должны быть отделены от HTTP-обработчиков.
5. Тесты должны быть отделены от исходного кода приложения.
6. Конфигурация не должна содержать секреты непосредственно в исходном коде.
7. Новые компоненты должны размещаться в соответствующих каталогах.

## 6. Принцип изменения структуры

Изменение структуры проекта допускается при необходимости расширения функциональности или улучшения архитектуры.

Существенные изменения должны быть согласованы с архитектурной документацией и зафиксированы в истории проекта.
