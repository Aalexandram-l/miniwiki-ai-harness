# MiniWiki — Процесс разработки

## 1. Общие положения

Разработка MiniWiki ведётся поэтапно с использованием Git и GitHub.

Каждый этап имеет отдельную ветку, набор задач и критерии завершения.

Основная цель процесса — обеспечить прозрачность изменений, контроль качества и возможность отслеживать историю разработки.

## 2. Организация Git-веток

Для проекта используется следующая схема:

- `main` — основная стабильная ветка проекта.
- `stage-1-architecture` — архитектура и технологический стек.
- `stage-2-rules-memory` — правила проекта и контекстная память.
- `stage-3-skills` — навыки ИИ-агента.
- `stage-4-miniwiki` — реализация приложения MiniWiki.

Новые ветки создаются от актуальной версии `main`.

## 3. Правила коммитов

Коммиты должны быть небольшими, логически завершёнными и отражать конкретное изменение.

Рекомендуемый формат:

```text
type: краткое описание изменения
```

Допустимые типы:

- `feat` — новая функциональность;
- `fix` — исправление ошибки;
- `docs` — изменение документации;
- `test` — добавление или изменение тестов;
- `refactor` — изменение структуры кода без изменения поведения;
- `chore` — технические изменения и настройки.

Примеры:

```text
docs: add project architecture
docs: describe technology stack
chore: configure Python project
test: add initial application tests
```

## 4. Порядок работы над этапом

1. Переключиться на актуальную ветку `main`.
2. Получить последние изменения из GitHub.
3. Создать отдельную ветку для этапа.
4. Выполнить запланированные задачи.
5. Проверить изменённые файлы.
6. Запустить необходимые автоматические проверки.
7. Создать коммит.
8. Отправить ветку на GitHub.
9. Создать Pull Request в `main`.
10. Проверить изменения и выполнить слияние.

## 5. Pull Request

Каждый этап разработки должен завершаться Pull Request.

Pull Request должен содержать:

- название этапа;
- описание выполненной работы;
- список основных изменений;
- результаты проверок;
- известные ограничения и нерешённые проблемы.

Слияние выполняется после проверки изменений.

## 6. Проверки качества

В зависимости от этапа используются следующие проверки:

- Pytest — автоматические тесты;
- Ruff — проверка качества Python-кода;
- проверка конфигурации Docker;
- проверка структуры каталогов;
- ручная проверка документации;
- проверка отсутствия секретных данных в Git.

Проверки должны выполняться до отправки Pull Request.

## 7. Работа с документацией

Документация проекта ведётся на русском языке.

Названия файлов, каталогов, классов, функций, переменных и Git-веток могут использовать английский язык в соответствии с общепринятыми практиками разработки.

Архитектурные изменения должны отражаться в соответствующих документах.

## 8. Работа с ИИ-агентом

При использовании ИИ-агента необходимо:

- учитывать правила проекта;
- проверять контекстную память перед началом работы;
- использовать подходящие Skills;
- не изменять файлы без понимания их назначения;
- запускать проверки после внесения изменений;
- документировать важные решения и обнаруженные проблемы.

## 9. Завершение этапа

Этап считается завершённым, если:

- все запланированные задачи выполнены;
- документация обновлена;
- необходимые проверки пройдены;
- изменения отправлены в GitHub;
- Pull Request проверен и объединён с `main`.
