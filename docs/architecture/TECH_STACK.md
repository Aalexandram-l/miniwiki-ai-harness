# MiniWiki — Технологический стек

## 1. Общая информация

Для разработки MiniWiki выбран стек технологий, позволяющий создать лёгкое, безопасное и расширяемое веб-приложение.

Основные критерии выбора:

- простота разработки и сопровождения;
- надёжность;
- безопасность;
- наличие документации и сообщества;
- возможность автоматического тестирования;
- совместимость с инструментами разработки с использованием ИИ-агента.

## 2. Основные технологии

### 2.1. Python 3.12

Основной язык программирования проекта.

Причины выбора:
- простой и понятный синтаксис;
- развитая экосистема библиотек;
- удобство написания автоматических тестов;
- широкие возможности интеграции с ИИ-инструментами.

### 2.2. FastAPI

Используется для создания серверной части приложения и REST API.

Причины выбора:
- высокая производительность;
- автоматическая генерация документации API;
- встроенная поддержка проверки входных данных;
- поддержка асинхронных операций.

### 2.3. SQLite

Используется в качестве основной базы данных на начальном этапе проекта.

Причины выбора:
- не требует отдельного сервера;
- простая настройка;
- хранение данных в одном файле;
- подходит для небольшого приложения.

### 2.4. SQLAlchemy

Используется для взаимодействия с базой данных.

Причины выбора:
- поддержка ORM;
- удобная работа с моделями данных;
- возможность перехода на другую СУБД при необходимости.

### 2.5. Jinja2

Используется для формирования HTML-страниц на стороне сервера.

Причины выбора:
- разделение логики и представления;
- поддержка шаблонов и наследования;
- интеграция с FastAPI.

### 2.6. HTMX

Используется для добавления интерактивности без необходимости создавать отдельное SPA-приложение.

Причины выбора:
- уменьшение количества JavaScript-кода;
- работа через HTTP-запросы;
- простая интеграция с серверными HTML-шаблонами.

### 2.7. CSS

Используется для оформления пользовательского интерфейса.

На начальном этапе отдельный CSS-фреймворк не требуется.

### 2.8. Pytest

Используется для автоматического тестирования.

Причины выбора:
- простой синтаксис тестов;
- поддержка фикстур;
- возможность тестирования API и бизнес-логики.

### 2.9. Ruff

Используется для проверки качества и форматирования Python-кода.

Причины выбора:
- быстрая работа;
- единый инструмент для нескольких видов проверок;
- интеграция с процессом разработки.

### 2.10. Docker

Используется для контейнеризации приложения.

Причины выбора:
- воспроизводимость окружения;
- упрощение запуска;
- удобство развёртывания.

## 3. Рассмотренные альтернативы

| Область | Выбранная технология | Альтернативы |
|---|---|---|
| Backend | FastAPI | Django, Flask |
| База данных | SQLite | PostgreSQL |
| Шаблоны | Jinja2 | React |
| Интерактивность | HTMX | Vue.js |
| Тестирование | Pytest | unittest |
| Контейнеризация | Docker | Запуск без контейнеров |

## 4. Ограничения выбранного стека

- SQLite может стать ограничением при высокой конкурентной нагрузке.
- HTMX не предназначен для сложных клиентских интерфейсов уровня SPA.
- Docker требует дополнительной настройки окружения.
- SQLAlchemy добавляет дополнительный уровень абстракции при работе с базой данных.

## 5. Возможности дальнейшего развития

При увеличении нагрузки и функциональности приложения допускается:

- переход с SQLite на PostgreSQL;
- расширение REST API;
- добавление новых механизмов аутентификации;
- внедрение дополнительных инструментов мониторинга;
- расширение автоматизированных проверок.

## 6. Принцип изменения технологического стека

Изменение выбранной технологии допускается при наличии обоснованной причины.

Существенные изменения необходимо фиксировать в документации архитектурных решений.
